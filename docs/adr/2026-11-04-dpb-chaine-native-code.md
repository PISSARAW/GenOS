# DPB : qualifier la chaîne native de réparation de code

Statut : retenu pour le protocole DPB natif. La campagne de résultats reste distincte du développement.

La campagne par composants ne démontre pas le fonctionnement de l'orchestrateur de production. Le nouveau bras C doit exécuter une vraie mission locale par MCP, conserver les refus et livrer uniquement un artefact dont les preuves correspondent aux fichiers exportés.

Le worker typé conserve les admissions ADN, les plafonds canoniques et la décision allostatique. Le protocole demande un worker adaptatif, puis l'intégrateur final natif avec GQEL. Il ne force pas trois workers lorsque le runtime refuse cette capacité. Les critiques utilisent deux contextes Qwen de la même famille : cela représente un seul groupe de dépendance, pas deux modèles indépendants.

Les tests publics CommonJS forment un domaine de vérification fini, scellé avant la génération. Les chemins et hashes des tests sont immuables ; les sources de production sont explicitement mutables. Deux processus vérificateurs distincts exécutent les tests dans des copies séparées, avec des ordres inversés. Leurs processus Node enfants sont comptabilisés séparément. Une sentinelle de fin empêche qu'un `process.exit(0)` remplace l'exécution des assertions. Cette preuve ne couvre pas les huit oracles cachés du benchmark.

Le reçu de l'intégrateur doit porter sur son propre artefact. Son contrat de sources entre dans l'enveloppe d'autorité avant exécution. L'observation, l'attestation indépendante, le rejeu et la décision restent liés au même agent, run, rapport et autorité. Un reçu du worker ne suffit pas à qualifier un code réécrit ensuite par l'intégrateur.

Le rejeu précède la décision terminale. Il vérifie réellement la chaîne CLI, restaure le snapshot du code dans un nouveau répertoire confiné, réexécute les commandes autorisées et compare les empreintes du snapshot, de la restauration et du workspace source. Les exigences existantes de promotion ne sont pas désactivées. L'accès au snapshot d'une matérialisation GQWF exige une session active appartenant au même agent, au même workspace et à un run en cours, une lease ouverte et son marqueur de propriété.

La décision de retenir provisoirement le candidat est réellement persistée par `genos_record_decision`. Elle cite les preuves et reste conditionnée aux portes finales. Un bloc de contenu MCP est décodé puis validé comme reçu typé ; un simple succès de transport ne remplace pas cette validation. L'événement terminal authentifié est conservé au point exact d'acceptation, après enrichissement des preuves de qualité.

GQEL distingue les contrôles de lecture de code des contrôles littéraires. Les critiques reçoivent les sources lisibles et la vérification d'exécution liée au digest courant. Les notes absentes ne sont jamais inventées : le schéma exige une note entière pour un verdict connu sur un critère souple. La porte du rapport reconnaît les négations comme des mots, afin de ne pas traiter `node` ou `genos` comme une négation.

La négation française composée `ne…pas` compte pour une seule unité de polarité. La suite globale a révélé cette régression après le premier correctif de frontières de mots : la série native v1 a été interrompue, conservée sans jugement caché et remplacée par un nouveau protocole v2. L'objectif canonique est transmis au worker avant l'ajout de son identité et reste disponible aux reprises ; le contrat DPB fixe leur rôle topologique d'implémentation. Les plafonds, admissions et refus GQWF restent actifs.

Les trois bras partagent les mêmes fixtures, consignes publiques et plafonds globaux d'appels, de tokens et de durée. Le bras B appelle le composant CodeProof et les tests publics ; C appelle toute la chaîne native applicable. Tous les tests fournis, y compris le wrapper de régression, sont immuables. On ne revendique donc pas la création d'un test de régression par le modèle.

Les réponses, appels, coûts inconnus, refus et interruptions sont conservés. Les contrôles par réponses enregistrées sont explicitement séparés des contrôles Qwen réels et des 90 essais primaires. Les oracles cachés n'interviennent qu'après toutes les sélections finales. La comparaison porte sur les traitements complets ; trois tâches ne justifient pas une généralisation statistique à tous les bugs.

Trinity, l'évolution intergénérationnelle et les autres concepts non nécessaires ne sont pas déclarés exécutés par simple présence dans un catalogue. Un contrôle Trinity de code sans mesures sémantiques a été refusé pendant le développement ; aucune mesure de remplacement n'est fabriquée.
